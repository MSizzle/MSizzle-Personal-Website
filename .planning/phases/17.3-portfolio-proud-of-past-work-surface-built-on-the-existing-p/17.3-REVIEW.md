## Warnings

### WR-01: `groupProjectsByYear` duplicated verbatim across two routes

**File:** `src/app/portfolio/page.tsx:27-38`
**Also in:** `src/app/projects/page.tsx:25-36`

**Issue:** The 12-line `groupProjectsByYear` function is a character-for-character copy from the existing projects page. Any future logic change (e.g., grouping by a Notion `Date` property instead of `lastEdited`) must be applied in both files. If only one is patched, the two routes will silently diverge in their year-bucketing behavior with no compile-time or runtime warning.

**Fix:** Extract to a shared module and import in both pages:

```ts
// src/lib/group-projects-by-year.ts
import type { Project } from "@/lib/notion-projects";

export function groupProjectsByYear(projects: Project[]): Map<number, Project[]> {
  const groups = new Map<number, Project[]>();
  for (const project of projects) {
    if (!project.lastEdited) continue;
    const year = new Date(project.lastEdited).getUTCFullYear();
    if (Number.isNaN(year)) continue;
    const bucket = groups.get(year) ?? [];
    bucket.push(project);
    groups.set(year, bucket);
  }
  return new Map([...groups.entries()].sort(([a], [b]) => b - a));
}
```

Then in both page files:
```ts
import { groupProjectsByYear } from "@/lib/group-projects-by-year";
```

### WR-02: `next/link` mock in `portfolio.test.tsx` typed as `any`

**File:** `src/__tests__/pages/portfolio.test.tsx:23`

**Issue:** The `next/link` mock destructures props as `: any`, discarding type safety:

```ts
// current -- loses all type information
default: ({ children, href, ...props }: any) =>
  React.createElement("a", { href, ...props }, children),
```

The equivalent mock in `section-work.test.tsx:6-17` (written in the same phase) properly types the same mock with an explicit interface. The inconsistency means TypeScript cannot catch prop-shape mistakes in `portfolio.test.tsx`'s mock if the test is later extended.

**Fix:** Apply the same typed interface used in `section-work.test.tsx`:

```ts
vi.mock("next/link", () => ({
  default: function LinkMock({
    children,
    href,
    ...props
  }: {
    children: React.ReactNode;
    href: string;
    [key: string]: unknown;
  }) {
    return React.createElement("a", { href, ...props }, children);
  },
}));
```

## Info

### IN-01: Silent empty `catch {}` in `PortfolioPage` is effectively dead code

**File:** `src/app/portfolio/page.tsx:47-49`

**Issue:** The outer `try/catch {}` that guards `getFeaturedProjects()` will never fire in production. `getFeaturedProjects()` already has its own internal try/catch that returns `[]` on any error (see `src/lib/notion-projects.ts:186-218`). The outer catch is therefore unreachable under all documented failure modes. When it does catch something truly unexpected, no log or trace is emitted -- making the failure invisible.

This matches the `/projects/page.tsx` convention exactly, so it is a pre-existing pattern choice, not a regression. However, adding even a minimal server-side `console.error` inside the catch would make unexpected failures observable.

**Fix (optional):**
```ts
try {
  projects = await getFeaturedProjects();
} catch (err) {
  console.error("[portfolio] unexpected error in getFeaturedProjects:", err);
  // projects stays []
}
```

### IN-02: "All work" CTA copy is semantically mismatched with the curated destination

**File:** `src/components/home/section-work.tsx:73`

**Issue:** `<Button href="/portfolio">All work</Button>` -- the label "All work" implies a complete archive, but `/portfolio` is a curated selection. The full archive is at `/projects`. This is intentional per the phase spec (D-01), but a visitor who clicks "All work" and sees only featured projects may be confused.

**Fix (copy judgment call):** Consider copy that matches the destination's curatorial premise, such as "Selected work", "Portfolio", or "See portfolio". This is a product decision, not a code bug.

### IN-03: `portfolio.test.tsx` is silently coupled to real `PageHero` DOM structure

**File:** `src/__tests__/pages/portfolio.test.tsx:71-73`

**Issue:** The SC-1.3 assertion relies on `PageHero` rendering an `<h1>`:

```ts
const h1 = screen.getByRole("heading", { level: 1 });
expect(h1.textContent).toContain("Portfolio");
```

`PageHero` is NOT mocked, so the test verifies integration, not just the page. If `PageHero` ever changes its heading element (e.g., to `<h2>` for a redesign), this test will throw `TestingLibraryElementError` with no explanation. A comment documenting the coupling would help future maintainers understand why the test breaks when `PageHero` changes.

**Fix:** Add an inline comment:

```ts
// Relies on PageHero rendering an <h1>; update if PageHero heading level changes.
const h1 = screen.getByRole("heading", { level: 1 });
```
