## Architecture Patterns

### Pattern 1: Next.js Config-Level Redirects

**What:** Use `async redirects()` function in `next.config.ts` to register all 301 redirects centrally.

**When to use:** For bulk permanent redirects (SEO-friendly); avoids middleware overhead and is idiomatic in Next.js App Router.

**Example:**
```typescript
// next.config.ts (already has one example — extend it)
async redirects() {
  return [
    { source: '/blog', destination: '/writing', permanent: true },    // existing
    { source: '/events', destination: '/', permanent: true },          // new
    { source: '/photos', destination: '/', permanent: true },          // new
    { source: '/links', destination: '/about', permanent: true },     // new
    { source: '/newsletter', destination: '/writing', permanent: true }, // new
    { source: '/watching', destination: '/uses', permanent: true },   // new
  ]
}
```

**Critical detail:** `permanent: true` maps to HTTP 301 (searchable redirect). Vercel honors this at edge runtime.

**Source:** [VERIFIED: Next.js 16 Redirects](https://nextjs.org/docs/app/api-reference/config/next-config-js#redirects) — official Next.js documentation for App Router redirects.

### Pattern 2: Route Deletion via Directory Removal

**What:** Delete the `src/app/[route]/` directory entirely; Next.js App Router will 404 any request to that path.

**When to use:** For routes that should never exist (no redirect, no data). Example: `/specimen` and `/v3-specimen` are internal design-system pages that were never meant to be public.

**How:** Delete `src/app/specimen` and `src/app/v3-specimen` directory trees. Verify no `href="/specimen"` links remain in the codebase (grep confirms none currently reference these).

**Source:** [VERIFIED: Next.js App Router Structure](https://nextjs.org/docs/app/building-your-application/routing) — deleting a route directory removes that path entirely.

### Pattern 3: Sitemap & Robots Metadata Sync

**What:** `src/app/sitemap.ts` and `src/app/robots.ts` are static metadata exports. When routes change, these exports must be updated in lockstep.

**When to use:** Every route deletion or redirect must trigger updates here to avoid stale metadata (searchability + crawlability regressions).

**Example — sitemap.ts:**
```typescript
const staticRoutes: MetadataRoute.Sitemap = [
  // REMOVE these lines:
  // { url: `${SITE_URL}/events`, ... },
  // { url: `${SITE_URL}/photos`, ... },
  // { url: `${SITE_URL}/links`, ... },
  // { url: `${SITE_URL}/newsletter`, ... },
  // { url: `${SITE_URL}/watching`, ... },

  // KEEP these:
  { url: SITE_URL, lastModified: new Date(), changeFrequency: 'weekly', priority: 1 },
  { url: `${SITE_URL}/about`, ... },
  { url: `${SITE_URL}/writing`, ... },
  { url: `${SITE_URL}/uses`, ... },
  { url: `${SITE_URL}/projects`, ... },
  // … etc
]
```

**Example — robots.ts:**
```typescript
export default function robots(): MetadataRoute.Robots {
  return {
    rules: { userAgent: '*', allow: '/', disallow: ['/specimen', '/api/'] },
    // /v3-specimen is NOT listed because it will 404 anyway
    sitemap: `${SITE_URL}/sitemap.xml`,
  }
}
```

**Source:** [VERIFIED: Next.js Metadata](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots) — official pattern for dynamic sitemap/robots.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Route redirects | Custom middleware or per-route `redirect()` | `async redirects()` in next.config.ts | Config-level redirects are cached at CDN edge; per-route `redirect()` adds latency and requires visiting each route |
| 404 behavior | Custom error pages for each deleted route | Let Next.js App Router natural 404 | Deleting the directory is cleaner; default 404 handling is sufficient |
| Sitemap/robots generation | Hand-coded JSON/XML files | Next.js `MetadataRoute` exports | Auto-generates at build time; no manual XML maintenance |
| Link management | Manual string replacement | Grep + editor find-replace (or automated refactoring) | Links are scattered across 7 files; IDE refactoring tools catch them reliably |

## Common Pitfalls

### Pitfall 1: Forgetting the Redirect After Route Deletion
**What goes wrong:** Route directory is deleted but no redirect is added to `next.config.ts`. Old inbound links (e.g., from external sites linking to `/events`) result in 404 instead of 301 to new home.

**Why it happens:** Confusion between "hard delete" (404) and "redirect" (301). This phase mixes both: /specimen and /v3-specimen are hard-deletes, but /events and /photos need 301s for SEO.

**How to avoid:** For each cut route, ask: "Are external sites likely linking to this?" — If yes, add a 301 redirect. If it's internal-only (like /specimen), hard-delete is fine.

**Warning signs:** Domain authority drops; Google Search Console shows 404 errors for previously indexed URLs.

### Pitfall 2: Stale Sitemap Entries
**What goes wrong:** `src/app/sitemap.ts` still lists `/events`, `/photos`, `/newsletter` etc. Googlebot indexes stale routes; users can click sitemap links that now 404 or redirect.

**Why it happens:** Routing updates happen fast; metadata is easy to forget. Tests may not catch this if test assertions aren't updated.

**How to avoid:** Update `sitemap.ts` in the same commit as the redirects. Run the sitemap.test.ts suite to verify.

**Warning signs:** `src/app/sitemap.ts` still has entries like `{ url: `${SITE_URL}/events` ... }`. Vitest assertions fail: "expected static-looking entries >= 9" but now we have fewer.

### Pitfall 3: Forgotten Component Links
**What goes wrong:** V3Footer, Navigation, or EditorialHeader still have `<Link href="/links">` or `<Link href="/events">` calls. Users click nav links → hit redirects → bad UX + extra latency.

**Why it happens:** 7 files reference cut routes; it's easy to miss one. Grep finds them, but updating is tedious.

**How to avoid:** (1) Grep for all occurrences before starting (done in research); (2) Update all 7 in the same task; (3) Test nav/footer visually on mobile and desktop.

**Warning signs:** Footer or mobile drawer still shows "Events" link or "Watching" link even after deletion. Users report unexpected redirects.

### Pitfall 4: Test Assertion Breakage
**What goes wrong:** `sitemap.test.ts` has this assertion: `expect(staticLooking.length).toBeGreaterThanOrEqual(9)` but after deletions, we now have 6 static routes instead of 11. Test fails with cryptic "expected 6 to be >= 9".

**Why it happens:** Phase 17 added SEO regression tests; they assert route counts and specific entries. Route changes aren't reflected in the assertions.

**How to avoid:** Update all test assertions in lockstep with route deletions. Specifically:
- `sitemap.test.ts`: Change the >= count from 9 to 6 (or count dynamically)
- `sitemap.test.ts`: Remove the `/watching` entry test
- `robots.test.ts`: No changes needed (only /specimen disallow matters)
- `footer.test.tsx`: Remove assertions for `/watching`, `/photos`, `/newsletter`
- `navigation.test.tsx`: Remove assertions for deleted routes
- Delete `links.test.tsx` entirely (the /links page no longer exists)

**Warning signs:** `npm run test` fails with "expected X to be >= Y" or "link not found" after deleting a route directory.

### Pitfall 5: Metadata Export Inconsistency
**What goes wrong:** Some pages export canonical metadata like `alternates: { canonical: '/events' }` but the route is deleted. Pages have orphaned metadata pointing to dead URLs.

**Why it happens:** Metadata is in each route's `page.tsx` file; easy to overlook when deleting the file.

**How to avoid:** When deleting a route directory, all its metadata goes with it. No action needed. Only concern: if a page's metadata is being repurposed (e.g., /newsletter content moving to /writing), update the metadata in the target file.

**Example:** `/writing/page.tsx` should keep its canonical `"/writing"` (no change). `/newsletter/page.tsx` is deleted entirely (so its metadata is gone too).

**Warning signs:** Removed files still appear in `grep` results for canonical URLs.
